# 摄像头帧率实测与高帧率采集

本目录记录外接摄像头（**camera 0**）的极限帧率实测结果，以及一套**采集/显示分离**的高帧率采集方案，供视觉主程序（`visual_main.py`）接入参考。

> 注意：外接摄像头现在的索引是 **camera 0**（之前是 1，Windows 枚举变了）。任何用到摄像头索引的代码都要确认当前值。


## 相机能力实测结果（camera 0，MJPG）

真实原生分辨率共 9 档（640×400 等中间值会被协商到邻近档）：

| 协商分辨率 | 请求帧率 | **实测持续帧率** |
|------------|----------|------------------|
| 352×288    | 400      | **204.1** |
| 320×240    | 400      | **203.9** |
| 640×360    | 400      | **203.7** |
| **640×480** | 400     | **203.4** |
| 1280×1024  | 200      | 192.1 |
| 1280×960   | 200      | 192.1 |
| 1280×720   | 200      | 191.5 |
| 800×600    | 200      | 192.0 |
| 960×540    | 200      | 191.6 |

## 关键结论

1. **640×480 MJPG 是最优组合**。所有 MJPG 分辨率实测都卡在 ~204fps——瓶颈在 `read()` 管线本身（~4.9ms/帧），**不在分辨率**。所以选最高的 640×480 白拿更多像素，帧率一分不降。
2. **YUYV 到不了 200fps**。YUYV 640×480 实测只有 **60fps**（614KB/帧 × 60 ≈ 295Mbps，正好顶死 USB2.0 有效带宽）。要高速必须用 MJPG。
3. **相机标称 400fps 是虚标**，实际链路稳定给 ~204。对此任务 200fps 足够，无需追高。
4. **MSMF 下 `cap.get(FOURCC)` 读回不可靠**：MJPG 读回 `-`，且"高分辨率 YUYV 实测 192fps"是假象——相机忽略了格式请求实际仍输出 MJPG（原始 YUY2 1280×960@192 需要 ~3.8Gbps，物理不可能）。判断格式要看实测帧率而非读回值。
5. **帧率需用实测值，不信 `cap.get(FPS)`**。脚本用 `perf_counter` 实测，`FPS_TARGET=1000` 逼相机协商出上限。

## 采集/显示分离方案

高帧率采集不能"采集+显示"串在一个循环里（显示会拖垮采集）。核心结构：

```
┌─────────────┐    ┌─────────────┐    ┌──────────────┐
│ 采集线程      │    │ 主循环       │    │ 显示(节流)    │
│ cap.read()  │───▶│ 只取最新帧    │───▶│ 每N帧 imshow │
│ 只存最新一帧  │    │ 处理/打印fps │    │ waitKey      │
└─────────────┘    └─────────────┘    └──────────────┘
```

- **采集线程**独占 `cap.read()`，只保留最新一帧 + 累计计数，旧帧自然丢弃；
- **主循环**取最新帧做处理（后续接 YOLO/巡线算法），显示按 `--div` 节流；
- 采集链路因此不受显示/处理速度影响，稳定 ~204fps。

## 关键坑：主循环死循环会饿死采集线程（GIL 饥饿）

**现象**：窗口模式下采集从 ~204fps 掉到 **~35fps**，显示跟着掉到 ~9fps。

**根因**：主循环若 `while True` 忙等（无 sleep），会疯狂抢占 Python 的 GIL。`cap.read()` 虽在采集线程，但每帧都要 GIL 来存帧/计数/开下一轮 read，抢不到时间片就被饿死。

**修复**：主循环开头必须 `time.sleep(0.001)` 让出 GIL。

```python
while True:
    time.sleep(0.001)   # 关键: 让出 GIL, 否则死循环饿死采集线程 (实测掉到~35fps)
    with g.lock:
        f = g.frame
        cur_cap = g.count
    ...
```

**验证数据**：

| 主线程行为 | 采集 fps |
|------------|----------|
| headless（sleep 1s，几乎不占 GIL） | 205 |
| 死循环忙等（无 sleep） | 35~44 |
| `sleep(0.001)` | **204** |

## 200fps 实时 YOLO 处理管线（test_yolo.py）

采集能到 204fps，但 **YOLO 单帧推理本身 ~11.7ms（≈63fps）**。要让处理也追上采集，
光加线程没用（GPU 是延迟主导，实测 4 线程单帧才 ~104fps），靠的是**批量推理**。
test_yolo.py 把整条管线拆开，让采集、推理、保存、显示互不拖累：

```
┌──────────────┐   ┌──────────────┐   ┌─────────────────────────┐   ┌─────────┐
│ 采集线程       │──▶│ 有界分发队列    │──▶│ N个推理worker线程         │──▶│ 后台保存  │
│ 独占read,每帧入队│   │ 满才丢最旧帧    │   │ 各自独立模型, 机会式小批量predict│   │ imwrite │
└──────────────┘   └──────────────┘   └────────────┬────────────┘   └─────────┘
                                                     │ 每个worker发布最新标注帧
                                                     ▼
                                         主循环按固定节拍弹窗 (~60fps)
```

### 各环节设计

| 环节 | 做法 | 为什么 |
|------|------|--------|
| 采集 | 独立线程独占 `cap.read()`，每帧直接入有界队列 | 采集链路不受推理/显示影响，稳定 ~204fps |
| 队列 | 有界（`workers×batch×2`），满则丢最旧帧 | 延迟恒定不堆积；兜底丢帧只发生在这里 |
| 推理 | N 个 worker 各持**独立模型实例**，机会式小批量 | 多线程共享一个模型会内部状态竞态；批量吃满 GPU |
| 保存 | 后台线程 `imwrite` | 写盘不占推理时间 |
| 显示 | 全部 worker 发布最新帧到共享槽位，主循环按 ~60fps 节拍显示 | 显示帧率与 worker 节奏解耦，不卡顿 |
| 退出 | `stop_evt` + `get(timeout)` | 不用哨兵，避免队列满时收尾挂死 |

**机会式小批量**是吞吐的关键：worker 取到 1 帧**立即**处理（保持低延迟），推理前顺手
把队列里已有的帧最多带走 `batch-1` 个，一次前向吃掉一批。负载轻 = 单帧低延迟；
负载重 = 自动凑批吃满 GPU。

### 实测吞吐（8 worker × batch 4，本机 CUDA）

- 单帧 predict ≈ 11.7ms → 单线程 63fps；**FP16 反而更慢（15.7ms），别开**；TensorRT 未装
- 4 线程单帧（无批处理）≈ 104fps —— 多线程共享同一块 GPU 帮不上忙
- **只有批处理能榨出 GPU**：1 线程 batch8 ≈ 540fps、4 线程 batch4 ≈ 386fps
- 最终 8 worker × batch4：采集 ~192-205fps、处理 ~180-196fps，**覆盖率 99%+**

### 三个最容易踩的坑

1. **首次 predict 必须预热**：CUDA 上下文/算子初始化要 ~3s，不预热会把测试窗口吃光。
   预热 = 启动前对黑帧跑一次 `model.predict`。
2. **主循环必须 `time.sleep(0.001)`**：否则死循环抢占 GIL，采集线程被饿死掉到 ~35fps。
3. **收尾别用队列哨兵**：采集>处理时队列收尾往往正满，`put(None)` 会永久阻塞挂死。
   用 `stop_evt` + `get(timeout=0.2)` 让 worker 自行退出。

### 接入其他视觉任务（巡线/撞球/抓球/穿门…）的模板

这套结构与 YOLO 无关，换掉 `run_batch` 里的算法即可复用骨架：

- **模型类**（YOLO/分类/分割）：保持 worker 池 + 机会式小批量，把 `model.predict(frames,...)`
  换成你的推理调用，其余环节原样不动；
- **传统视觉**（巡线、找门框等，单帧几 ms）：可简化——采集线程供帧、单 worker 逐个处理
  即够，不需要批量；
- **实时性要自己守**：处理跟不上的帧**主动丢最旧帧**（有界队列），而不是无限积压把延迟
  越拖越大；
- 每个任务一个独立模块文件，只实现"输入一帧/一批 → 输出结果"，采集/队列/保存/显示复用
  同一套骨架。

## 视觉管线接入建议

1. 摄像头参数固定：`CAP_MSMF` + `MJPG` + `640×480` + `CAP_PROP_FPS=1000`；
2. 采集放独立线程独占 `cap.read()`：**每帧直接入有界队列**（不是只留最新帧），让算法端按
   自己节奏消费，队列满丢最旧帧保实时；
3. **重算法**（YOLO 等单帧 >5ms）：按上面 worker 池 + 机会式小批量搭，否则单线程只有
   ~63fps 甚至更低；**轻算法**（巡线等单帧几 ms）：单 worker 取帧处理即可；
4. 显示节流到 ~50-60fps，且**只由主循环定时取"最新一帧"显示**，不要边处理边 imshow；
5. **任何与采集同进程的主循环都必须周期 `sleep(0.001)`**，否则 GIL 饥饿把采集拖到 ~35fps；
6. 收尾用 `stop_evt` + 超时取帧，**不要用队列哨兵**（满队列会阻塞挂死）。
