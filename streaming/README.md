# streaming — 摄像头外置开发机，网络传帧到 S100

把**摄像头从 S100 板端移到开发机**：开发机以 ~200fps 采集并编码 JPEG，通过
**裸 TCP / UDP** 实时传给 RDK S100，S100 只负责接收 + 跑视觉任务（巡线/撞球/穿门/抓球/放球）。

```
┌─────────────── 开发机 ───────────────┐        ┌─────────────── RDK S100 ───────────────┐
│ dev_capture_send.py                  │        │ s100_receiver.py                        │
│                                      │  TCP/  │                                        │
│  相机(MJPG,~204fps) ──► JPEG ──► 发送 │ ─────► │  接收 ──► 解码 ──► P1/P2/P3/P4/P5 检测 ──► 结果输出
│   采集线程 → 最新帧槽 → 发送线程        │  UDP  │   后台接收线程 → 最新帧槽 → 处理主循环      │
└──────────────────────────────────────┘        └────────────────────────────────────────┘
```

## 文件说明

| 文件 | 端 | 作用 |
|------|:--:|------|
| `frame_protocol.py` | 共用 | 帧线协议（TCP 长度前缀帧 / UDP 分片重组）+ 发送器/接收器 |
| `dev_capture_send.py` | 开发机 | 200fps 采集 + JPEG 编码 + 发送 |
| `dev_test_receiver.py` | 开发机 | 本机回环测试接收 + 处理（验证协议） |
| `s100_tasks.py` | S100 | 任务处理管线（复用 V3.0 各任务检测器） |
| `s100_receiver.py` | S100 | 接收 + 解码 + 运行任务 + 输出结果 |

## 快速上手（本机回环测试，无真机）

先测链路通不通，再上真机。

```bash
# 终端 1：启动测试接收端（TCP 监听 0.0.0.0:8900）
python dev_test_receiver.py --proto tcp

# 终端 2：用视频文件代替相机，发到本机（无相机也能测）
python dev_capture_send.py --host 127.0.0.1 --proto tcp --source ..\v4.0\camera_front\result\front_detect_20260820_141643.mp4 --time 5

# 或换 UDP 再测一遍
python dev_test_receiver.py --proto udp
python dev_capture_send.py --host 127.0.0.1 --proto udp --source <任意视频> --time 5
```

正常输出：

```
[统计] 接收 204.0fps | 处理 204.0fps | 帧   32.5KB | 带宽  53.3 Mbps | 接收端丢弃    0 ...
```

接收端能看到帧解码、处理、无丢包即链路 OK。

## S100 部署

1. 把 `streaming/` 整个目录拷到 S100（例如 `/home/root/RC/visual_part/streaming`）
   - 注意 `s100_tasks.py` 依赖 `../V3.0` 的任务目录，必须放在 `视觉部分/` 同级结构下；
   - 若任务已迁移到 v4.0 等其他目录，改 `s100_tasks.py` 里的 `_V3` 路径即可。
2. S100 上启动接收端（建议放到开机自启/后台）：

```bash
cd streaming
python s100_receiver.py --proto tcp          # 监听全部网口 :8900，等待开发机
```

3. 开发机启动发送端：

```bash
python dev_capture_send.py --host <S100的IP> --proto tcp
```

> S100 IP 按实际网络填（板载 WiFi/网线/热点均可用 `--host` 指定）。
> 只要开发机和 S100 能 ping 通即可，`--host` 填 S100 的地址。

## TCP 还是 UDP？

| | TCP（默认） | UDP |
|---|---|---|
| 可靠性 | 不丢包，有序 | 丢包只丢帧，不重传 |
| 压力反馈 | 网络堵 → 发送端阻塞 → 主动丢最旧帧 | 无反馈，丢包发生在网卡/路由器 |
| 延迟 | 略高（重传 + 拥塞控制） | 最低 |
| 适合 | 有线 / 千兆链路 | 无线 / 带宽紧张、可容忍丢帧 |

**建议**：先用 TCP 跑通；若实测发送端丢帧多或延迟过大，再换 UDP 对比。

## 带宽估算（决定画质参数）

单帧带宽 ≈ 帧率 × 单帧大小：

| 分辨率 | JPEG 质量 | 单帧约 | @200fps 带宽 | 千兆有线 | WiFi |
|--------|:---:|------:|-----------:|:---:|:---:|
| 640×480 | 70 | 20~60KB | 32~96 Mbps | ✅ | ⚠️ 紧 |
| 640×480 | 50 | 12~35KB | 19~56 Mbps | ✅ | ✅ |
| 320×240 | 70 | 6~15KB | 10~24 Mbps | ✅ | ✅ |

链路不够时按顺序调整：
1. 降 `--quality`（如 70 → 50）；
2. 降 `--scale`（0.5 → 320×240，带宽降约 4x）；
3. 换 `--proto udp`。

## 线程与丢帧设计

- **发送端**：采集线程独占 `cap.read()`（只留最新一帧）；发送线程取最新帧 → 编码 → 发送。
  网络跟不上时新帧覆盖旧帧，旧帧自动丢弃，**延迟恒定不积压**。
- **接收端**：后台线程持续 drain socket（TCP 读字节流 / UDP 收分片并重组），只保留最新完整帧；
  处理主循环按自己节奏取最新帧。处理不过来时旧帧在接收端被覆盖丢弃，
  统计里 `丢帧` 数值能反映两端是否跟得上。
- **GIL 注意**：所有主循环/空转必须 `time.sleep(0.001)` 让出 GIL，
  否则死循环会饿死采集/接收线程（实测掉到 ~35fps），详见 `test/README.md`。
- **收尾**：统一用 `stop_evt` / `KeyboardInterrupt`，不用队列哨兵。

## 帧协议（frame_protocol.py）

**TCP**：`[18B 包头][JPEG 数据]`，包头含 magic(`RCV1`)、宽高、frame_id、负载长度。
**UDP**：每帧拆成 ≤1200B 数据报，分片头含 frame_id / 分片序号 / 分片总数，接收端重组，
超时 0.5s 未收全的残帧丢弃。

## 常见问题

- **发送端连不上 S100**：先 `ping <S100 IP>`；确认端口没被占用、S100 已先启动 `s100_receiver.py`。
- **接收端收不到帧**：三端 `--proto`/`--port` 必须一致；开发机 `--host` 填 S100 的 IP（不是 0.0.0.0）。
- **发送端丢帧多 / 带宽高**：按"带宽估算"一节降 `--quality` / `--scale`，或换 `--proto udp`。
- **S100 球检测被跳过**：需要板端 `hbm_runtime` 与 `best_nashe_320x320_nv12.hbm`；
  确认模型在 `V3.0/P2 撞球/` 下，或 `--tasks` 显式带上 p2/p4。
- **接收端帧率低于 200fps**：先看 `接收` 是否接近发送端帧率；若 `处理` 明显低于 `接收`，
  说明算法单帧耗时是瓶颈（丢帧由接收端丢弃兜底，属正常设计）。
